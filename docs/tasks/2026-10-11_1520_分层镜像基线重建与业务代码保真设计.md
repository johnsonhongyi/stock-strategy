# 分层镜像基线重建与业务代码保真设计

## 目标

保留固定运行时基线上的快速分层发布，同时在操作系统或运行依赖确需更新时，支持把一个**指定 Git 版本**重建为新的版本化单层 base。无论走哪条路径，线上业务代码都必须能追溯到同一份已审核源码，避免镜像压平、源码打包或手工复制时把业务逻辑悄悄换成别的版本。

本文是发布能力设计，不表示新的 base 重建命令已经实现或获准执行。当前线上服务仍按已验收发布版本运行。

## 当前发布结构与缺口

- API 固定从 stockstrategy/backend:flatbase-20261010171545 构建；已校验 base ID 为 sha256:ed8cbe9544efbcd5f4a50039b79884d43d1d2b662dc9ee6715325c1525d52d6d，包含 1 层。每个候选版本都从这个 base 建立一次性 builder，只替换 Go 可执行文件，候选镜像要求恰好 2 层，不从上一版 API 镜像继续叠层。
- builder 与生产容器隔离：发布脚本使用 docker cp 把编译产物送入临时 builder，再提交候选镜像；隔离 API 冒烟通过后才切换生产容器。生产容器根文件系统只读，数据库、日志、临时目录及 Web 缓存继续使用外置挂载。
- Web 静态文件按 release 目录外置挂载，不随 API 单层镜像压平。API 的当前镜像标签记录 release ID，但现有镜像配置没有 source commit 标签；回滚 manifest 也未记录本次应用的源码 SHA、后端二进制摘要和 Web 文件清单。因此不能只靠镜像标签证明线上业务源码版本。
- 最近几次压平出现业务偏差的风险点，是把运行中的容器状态、临时工作树或人工同步文件当作源码事实来源，或者只核对镜像层数而未核对完整源码身份和编译产物。层数正确不等于代码版本正确。

## 发布与新 base 的统一来源

每次构建都必须显式确定一个完整的 40 位 Git commit SHA，并将其作为唯一业务源码来源。分支名、日期标签、正在变化的工作目录和生产容器文件都不能代替该 SHA。

1. 在隔离的 detached worktree 检出指定 SHA。构建前记录 git rev-parse HEAD、Git tree SHA 和 git status --porcelain；要求 HEAD 等于指定值且工作树无未提交、未跟踪文件。不得把用户当前工作区的未提交改动混入发布包。
2. 由该 worktree 同时构建 Go API 与 Web。产物清单按仓库相对路径排序，逐项记录 SHA256；另记录 Go/Node/npm 版本、编译参数、后端二进制 SHA256、Web 发行物清单摘要和所用 runtime base 的不可变 image ID/digest。
3. 发布包携带机器可读的 release-manifest.json 与其 SHA256。源码 SHA、tree SHA、构建产物摘要、目标 release、base ID、预期镜像层数和回滚版本必须互相校验；校验失败立即停止，不更新服务器工作树或生产容器。
4. Windows 路径及 Unicode 文件名必须保真。清单生成和打包后要复核相对路径集合、文件数和逐文件摘要；不要把未经往返校验的 git archive/tar 重打包结果视为等价源码。任何文件名或摘要对不上都禁止发布。
5. 把源码 SHA、manifest SHA、base ID 和 release ID 写入镜像 labels 及部署回滚 manifest。健康信息应能报告构建 commit 与 release；若增加该运行时信息接口，需保持现有 API 兼容，并在本地和隔离环境验证后再上线。

## 快速分层发布门禁

- 在固定 base 没有变化时，继续使用临时 builder 产生一层应用差异；验证候选镜像的第一个 RootFS layer 与 pinned base 相同、层数为 base 层数 + 1，并核对镜像 label、manifest SHA 和候选容器内二进制 SHA。
- Web 发行物必须与 API 来自相同源码 SHA；部署前后分别校验 Web 文件清单，挂载到该 release 的新目录，避免覆盖上一个回滚版本静态文件。
- 保留现有只读隔离 API smoke test、API/Web 健康检查、Web→API 检查、完整挂载契约检查、回滚快照 SHA256 校验及失败自动回退。不得把真实数据卷挂入隔离 smoke test。
- 候选检查通过后再切换服务。记录 API/Web image ID、digest、层数、大小、SizeRw、挂载摘要、源码 SHA 和回滚命令。

## 指定版本压平为新 base

只有 runtime Dockerfile、系统库或运行依赖需要更新，或维护者明确批准调整基线时，才创建新 base。日常业务代码变更不触发压平。

1. 输入必须同时指定目标源码 SHA、目标 runtime Dockerfile 版本、当前基础 runtime digest、期望的新 base 标签及变更理由。新标签采用 flatbase-<release-id>，禁止覆盖旧标签。
2. 从干净 detached worktree 重新构建目标 SHA 的 API；若目标 base 代表完整产品版本，也一并构建相同 SHA 的 Web 发行物。不得从生产容器、回滚容器、旧镜像可写层或服务器源码目录提取业务文件。
3. 在无网络、无生产数据挂载的一次性构建环境中，基于目标 runtime 生成新 rootfs，并只把该 SHA 产生且摘要已核对的业务二进制写入 /app/easy-stock-backend。采用受控的 rootfs 导出/导入或等效单层构建时，必须显式重建用户、入口、环境变量、labels、健康检查及其他镜像配置；不能默认 docker export/import 会保留这些元数据。
4. 对新 base 做逐项验收：目标二进制 SHA 与构建 manifest 一致；镜像配置与 runtime 契约一致；RootFS 为 1 层；源码 SHA、tree SHA、manifest SHA 与标签一致；隔离 API smoke、只读根文件系统和所需运行时写路径检查通过。需要时在临时容器中对比压平前后的文件路径、权限、属主和内容摘要，除预先声明的 runtime 变化外不得有差异。
5. 新 base 先以候选标签保存，不立即替换当前 pinned base。再从该候选 base 构建同一目标 SHA 的 API 候选，完成统一健康与挂载验收；只有明确批准晋升后，才把部署配置的 pinned base ID 更新为新不可变 ID，并部署后续 release。
6. 保留旧 base、线上版本及其完整回滚依赖，直至回滚窗口结束且清单确认不再引用。禁止全局 prune；旧基线清理需按精确 image ID 和引用关系另行授权。

## 必须拒绝发布的情形

- 指定 SHA 与 worktree HEAD 不一致，工作树不干净，源码/产物清单不一致，或者 API/Web 不是同一源码 SHA。
- base tag 指向的 image ID/digest 与配置不符，候选层数或层顺序不符，容器内业务二进制摘要不符。
- 需要从线上容器中“捞回”业务文件，压平后无法解释文件差异，镜像元数据/挂载契约未重建，或健康/回滚门禁未通过。
