## 1. 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Linux x86_64 | 当前运行环境;脚本均为 bash/python3 |
| Python | 3.12 | 系统自带 `/usr/bin/python3` |
| Python 依赖 | 已 vendor | `~/.local/lib/python3.12/site-packages/`: numpy==1.26.4(锁定)、requests、pyyaml、pandas、lxml、matplotlib;随 home 持久,无需 pip |
| Node.js | 20+ | 仅 Web 工作台构建/运行需要 |
| Go 工具链 | 不需要 | 后端为预编译二进制 `bin/easy-stock-backend` |
| 网络 | 出站 443 | 数据源走 HTTPS;80/53 被拦截,DNS 走 DoH |

## 3. 配置文件(首次部署必填)

### 3.1 `easy-stock-service/.env`(权限 600)

```bash
A_STOCK_TOKEN=你的token      # 后端鉴权,每次调用时读取,不记值不打印
A_STOCK_ADDR=127.0.0.1:20081 # 监听地址,仅 loopback
```

### 3.2 `easy-stock-service/push_config.json`(权限 600)

企业微信群机器人 Key。只存本机,不记日志。推送通道:wecom(markdown 详细版+K线图 base64)。

### 3.3 `easy-stock-service/positions_real.json`

用户实盘持仓(手动维护)。只影响信号文案(持仓股:做T/加仓观察),不参与模拟账本。

### 3.4 `easy-stock-service/strategy.yaml`

策略参数版本 v1.3。改动规则:必须写 changelog(版本/日期/原因),用户批准才升版本;止损只收紧不放宽。

## 4. 启动步骤

```bash
# 1. 启动数据后端(幂等,已在运行则直接退出)
bash ~/workspace/easy-stock-service/start.sh
curl -sf http://127.0.0.1:20081/api/health   # 期望返回 ok

# 2. 启动 Web 工作台(会自动检查并拉起后端)
bash ~/workspace/easy-stock-web/start.sh
curl -sf http://127.0.0.1:20073/             # 期望返回页面

# 3. 一键自检(含自愈)
bash ~/workspace/easy-stock-service/recover.sh  # 期望 10/10 通过
```

两个 start.sh 都是幂等的,可反复执行。生产环境由定时巡检(见第6节)保活,手工启动一般只需要一次。

## 9. Windows 本机版本同步与 Docker 发布

跨项目职责、镜像标识、持久化和回滚总则见总控工作区的[全系统规范](../../../docs/engineering/全系统职责与Docker发布持久化回滚规范.md)。本项目负责 Go API、SBC/Web 和服务端 Python 行情任务；TK/ATS 是 Windows 桌面端，InStock 是独立 Python 选股项目，不应混用它们的镜像、数据库或运行状态。

### 9.1 默认方式：Git 版本对齐，不构建 Docker 镜像

- 每次发布先指定已审核的 Git commit SHA；检查本地/服务器分支、HEAD、未提交修改、运行容器、镜像 digest、健康状态和完整 bind mount 清单。工作区脏时先做外置备份并逐项确认，不强制覆盖。
- `stockstrategy-market-append` 等在 Docker 主机运行的 Python 任务从既有 `stock-strategy/source/` 工作树执行；其普通代码更新走该工作树的 Git 快进/版本同步，不因 Python 文件变化创建 Docker 镜像。cron 只有在任务时间或命令确实改变时才单独变更，代码同步不能顺手改 cron。
- Go API 与 Web 静态发行物必须从审核的同一个 Git SHA 生成并记录 source SHA。**现有 API/Web 容器使用只读根文件系统，发行物在镜像内，当前脚本没有已验证的容器内 Git/原子替换无镜像更新入口。**因此，不得把 `build-and-deploy.ps1` 当作普通 Git 更新模式；要保持只读根文件系统和既有挂载不变，Go/Web 的零镜像更新入口仍是待补齐的发布工具能力。该入口补齐前，普通 Go/Web 修改不能假称已按默认方式发布。
- 更新成功后记录：应用 Git SHA、当前 image tag/digest/labels、容器 ID、健康结果和挂载清单摘要。Git SHA 代表实际应用源码；image labels 只代表镜像构建时内容，两者不得互相冒充。

### 9.2 例外方式：明确需要分层开发/候选镜像时

只有运行环境或依赖必须改变，或用户明确要求对大型全系统联动改动进行隔离分层开发时，才使用此入口；它不是日常发布默认值。当前 `build-and-deploy.ps1` 仅实现这个 API 分层镜像例外：

```powershell
# 仅在已明确授权本次候选分层镜像后执行
pwsh -NoProfile -ExecutionPolicy Bypass -File .\build-and-deploy.ps1 -Server <Docker主机地址> -AllowLayeredImageBuild
```

脚本要求本地 `-AllowLayeredImageBuild` 与远端 `--allow-layered-image` 双重开关；获准后从固定 `flatbase-20261010171545` 生成唯一的 `stockstrategy/backend:<发布号>` 候选，预期 2 层，不为普通代码修复继续叠层。初次安装或更换基础运行环境另需独立授权。候选记录必须含理由、基础 image digest、Git SHA、tag、层数、验收结果和上一回滚点；未通过隔离/健康检查不得切换现网。

### 9.3 现存数据、回滚和磁盘检查

- SQLite 行情库、服务日志、锁状态、TDX 缓存以及 API/Web `/tmp`、`/run`、`/var/cache` 使用本项目既有外置 bind mount。发布必须逐项核对当前容器 mounts 并保持原样；不能新增/改名挂载或改变数据目录结构来实现代码发布。
- 代码回滚优先恢复上一个已验收 Git SHA/构建产物；运行依赖确有变化时才回到上一 image digest。无论哪种回滚，都接回同一外置数据路径，不恢复旧数据库覆盖新增数据。涉及 schema 迁移时先单独验证备份与兼容回退。
- 更新前后记录 `docker image inspect` 的 image size、`docker inspect --size` 的 `SizeRw`/`SizeRootFs`；`docker ps -s` 里的虚拟大小包含镜像和容器可写层，不能误认成新 image。镜像清理只允许对照精确清单删除无人使用且非回滚依赖的镜像，禁止全局 `docker image prune -a`、`docker volume prune` 和 `docker rm -v`。
- 健康检查/业务只读检查通过后，把 commit SHA、image digest、容器/挂载核对、镜像和写层体积、回滚命令及结果记入 `stock-strategy/ENVIRONMENT_HANDOFF.md`。不记录密钥或完整环境变量。

需要 PowerShell 7、Git、Node.js/npm、tar 和 OpenSSH 工具；Go 工具链由脚本按 `go.mod` 选择，缺少时从官方源下载并校验 SHA256。服务器需允许 root 的非交互 SSH 密钥登录，且 SSH 主机指纹必须匹配脚本内固定值；脚本不会把密码作为参数传输。
