## 3. 配置文件(首次部署必填)

### 3.1 `easy-stock-service/.env`(权限 600)

```bash
A_STOCK_TOKEN=你的token      # 后端鉴权,每次调用时读取,不记值不打印
A_STOCK_ADDR=127.0.0.1:20081 # 监听地址,仅 loopback
```

### 3.2 `easy-stock-service/push_config.json`(权限 600)

企业微信群机器人 Key。只存本机,不记日志。推送通道:wecom(markdown 详细版+K线图 base64)。

### 3.3 `easy-stock-service/positions_real.json`

用户实盘持仓(手动维护)。只影响信号文案(持仓股:做T/加仓观察),不参与模拟账本。

### 3.4 `easy-stock-service/strategy.yaml`

策略参数版本 v1.3。改动规则:必须写 changelog(版本/日期/原因),用户批准才升版本;止损只收紧不放宽。

## 4. 启动步骤

```bash
# 1. 启动数据后端(幂等,已在运行则直接退出)
bash ~/workspace/easy-stock-service/start.sh
curl -sf http://127.0.0.1:20081/api/health   # 期望返回 ok

# 2. 启动 Web 工作台(会自动检查并拉起后端)
bash ~/workspace/easy-stock-web/start.sh
curl -sf http://127.0.0.1:20073/             # 期望返回页面

# 3. 一键自检(含自愈)
bash ~/workspace/easy-stock-service/recover.sh  # 期望 10/10 通过
```

两个 start.sh 都是幂等的,可反复执行。生产环境由定时巡检(见第6节)保活,手工启动一般只需要一次。

## 9. Windows 本机版本同步与 Docker 发布

跨项目职责、镜像标识、持久化和回滚总则见总控工作区的[全系统规范](../../../docs/engineering/全系统职责与Docker发布持久化回滚规范.md)。本项目负责 Go API、SBC/Web 和服务端 Python 行情任务；TK/ATS 是 Windows 桌面端，InStock 是独立 Python 选股项目，不应混用它们的镜像、数据库或运行状态。

### 9.1 版本更新策略

- 服务端 Python 行情任务（如 stockstrategy-market-append）从服务器既有 source 工作树运行。普通 Python 代码同步不构建 Docker 镜像；cron、日历和外置运行配置只有在各自确需变更时另行处理。
- Go API 或 Web 代码需要上线时，使用 9.2 节已验证的“本机按指定源码构建 + 固定 base 快速分层发布”流程。Web 静态文件进入本次 release 的独立外置目录；API 镜像只从固定 base 增加一层应用差异。
- build-and-deploy.ps1 默认拒绝镜像构建，必须显式传入 -AllowLayeredImageBuild；远端还会检查 --allow-layered-image。每次生产发布都要有明确发布指令，不能把这个开关设成默认值。
- 当前脚本没有 SourceCommit 参数，也不会自动拒绝脏工作树；它会打包 Git 已跟踪文件和非忽略未跟踪文件。因此发布人必须先选定完整 commit SHA，并在隔离的发布工作副本中确认 source HEAD 等于该 SHA、git status --porcelain 为空。镜像 label 目前只记录 release ID，源码 SHA 必须人工记入交接记录。
- 禁止把 build-and-deploy.ps1 当成服务器 Git 同步或容器内热更新；禁止向生产容器 docker cp、从生产/回滚容器 docker commit，或将生产容器导出后当作新业务 base。

### 9.1.1 Git 主线与验证分支规则

- `main` 是唯一主线，也是后续集成、构建和发布的默认来源。`codex/*` 等新分支只用于隔离开发或测试验证，不作为默认发布目标。
- 每次新建或发现验证分支时，先告知用户分支名、基线提交、用途、与 `main` 的提交及文件差异、验证结果，并明确询问：将验证通过的改动合入 `main`，还是留在该分支继续验证。
- 用户明确选择前，只在该验证分支继续已授权的工作；不得自行合并、cherry-pick、rebase 到 `main`，也不得删除分支或其关联 worktree。用户选择继续验证时，保持 `main` 不变；验证结束或准备交付时再次汇报差异并询问是否合入。
- 用户选择合入后，先逐项比对分支独有提交和功能代码，确认没有遗漏；分支与 `main` 已分叉时，优先把缺失功能移植到 `main`，避免整体合并带入旧文件而回退主线。完成后做针对性验证、提交 `main`，记录最终 commit SHA。
- 清理验证分支前，确认其独有功能已进入 `main`、工作区没有未提交内容、没有仍在使用的关联 worktree；将分支清理作为单独操作告知用户，不与代码合入混做。

### 9.2 Go API/Web 实际验证流程：固定 base 快速分层发布

此流程用于发布 Go API 与 Web 代码。已验证发布样例为 release 20261011150918，源码提交 5c0c917eaad171b529c7939c470473bce66eddb3；每次发布仍须重新核对目标提交和服务器现况，不要复用样例中的 release ID。

1. 读取本文件 9.3 节和项目根目录 ENVIRONMENT_HANDOFF.md 最新记录。先在隔离的发布副本中检出目标源码 SHA，并人工核实：

       git -C .\source rev-parse HEAD
       git -C .\source status --porcelain

   第一条必须与本次指定的完整 40 位 SHA 相同；第二条必须没有输出。不要在正在开发、含未提交或未跟踪业务文件的工作树中构建。脚本不替操作者完成这两项核验。
2. 从 stock-strategy 项目根目录运行 PowerShell 7：

       pwsh -NoProfile -ExecutionPolicy Bypass -File .\build-and-deploy.ps1 -Server <Docker主机地址> -AllowLayeredImageBuild

   只有收到本次镜像发布指令后才运行。脚本会先校验固定 SSH 主机指纹、生产 API/Web 健康状态、always 重启策略、磁盘/内存空间及受管目录标记；这些检查未通过会在构建/部署前退出。
3. 本机按 source 仓库的 go.mod 选择 Go 版本并校验下载摘要，编译 Linux amd64 后端；运行 npm ci 和 npm run build 生成 Web 发行物。Web 使用 HttpOnly 会话 Cookie，脚本清除 VITE_A_STOCK_TOKEN，不向公开网页注入后台机器凭据；外网共享 Token 不可绕过用户登录，桌面 HMAC 协议保留。不得输出或记录真实凭据。源码包排除凭据文件、数据库、日志、截图及构建缓存。不要使用旧 dist 目录，也不要在构建失败后跳过构建继续发布。
4. 脚本将后端二进制、Web 静态文件、source 文件及部署辅助脚本打包并发送至服务器。远端先核对当前容器健康、挂载契约、容器写层和 pinned base ID；确认发布日历、market-append 脚本和 cron 与服务器持久配置一致；创建本次回滚快照并生成 SHA256SUMS。
5. API 候选必须从固定的 stockstrategy/backend:flatbase-20261010171545 构建。脚本在一次性 builder 中复制新编译的二进制，再提交候选镜像；脚本核对 pinned base 的 image ID 和单层要求、旧 API 与 pinned base 的首层关系，再从该 base 的一次性 builder 生成候选，并检查候选总层数为 base 层数加一（当前预期为 2 层）。不从上一版 API 镜像叠层。
6. 切换现网前，脚本在无外网、无生产数据库挂载的只读隔离容器中运行 API health smoke。通过后才替换 API/Web 容器：API 使用新候选镜像，Web 继续使用现有 nginx 镜像并挂载本 release 的版本化静态目录。切换后检查 API/Web 健康、Web 到 API 的 health 请求、只读根文件系统、完整外置挂载契约和容器写层。任一切换后门禁失败，脚本按回滚快照恢复旧容器及源码快照。
7. 命令成功后记录 release ID、目标源码 SHA、API/Web 镜像 tag/ID/digest/层数/大小、ReadOnlyRootfs、SizeRw/SizeRootFs、挂载清单摘要、API/Web/Web→API 健康结果、回滚快照校验及回滚命令到项目根目录 ENVIRONMENT_HANDOFF.md。不要记录密钥或完整环境变量。

如果本机 npm ci、Go 编译或 Vite 构建因 EPERM/进程权限失败，应停止本次发布，在干净隔离副本和可运行构建子进程的受控环境中，从同一个目标 SHA 重跑完整流程；不得复制旧构建产物补包。若远端预检失败，先按报错排除状态差异；不得绕过挂载、base ID、回滚快照或健康门禁。首次安装、更换 runtime 或晋升新 base 不属于本节普通分层发布，需要单独设计和审批。

### 9.3 现存数据、回滚和磁盘检查

- SQLite 行情库、服务日志、锁状态、TDX 缓存以及 API/Web `/tmp`、`/run`、`/var/cache` 使用本项目既有外置 bind mount。发布必须逐项核对当前容器 mounts 并保持原样；不能新增/改名挂载或改变数据目录结构来实现代码发布。
- 代码回滚优先恢复上一个已验收 Git SHA/构建产物；运行依赖确有变化时才回到上一 image digest。无论哪种回滚，都接回同一外置数据路径，不恢复旧数据库覆盖新增数据。涉及 schema 迁移时先单独验证备份与兼容回退。
- 发布脚本在切换失败时会自动回退。若发布成功后需要人工回滚，通过已核验的 SSH 身份登录 Docker 主机执行：

      bash /root/johnson/stock-strategy/docker/rollback-prebuilt.sh <本次release-id>

  回滚脚本会校验快照摘要和挂载契约，恢复本次发布前的 API/Web 版本，并把当前版本保留作前滚备份；不会回滚或覆盖持久数据库。
- 更新前后记录 `docker image inspect` 的 image size、`docker inspect --size` 的 `SizeRw`/`SizeRootFs`；`docker ps -s` 里的虚拟大小包含镜像和容器可写层，不能误认成新 image。镜像清理只允许对照精确清单删除无人使用且非回滚依赖的镜像，禁止全局 `docker image prune -a`、`docker volume prune` 和 `docker rm -v`。
- 健康检查/业务只读检查通过后，把 commit SHA、image digest、容器/挂载核对、镜像和写层体积、回滚命令及结果记入 `stock-strategy/ENVIRONMENT_HANDOFF.md`。不记录密钥或完整环境变量。

### 9.4 指定版本压平为新 base（设计状态）

当前脚本只支持从现有固定 base 构建单层应用差异；指定源码版本压平、生成并晋升新的 flatbase-<release-id> 尚未实现，不能把生产容器或旧镜像内容直接压成新业务基线。源码 SHA、构建清单、压平验收和晋升门禁设计见[分层镜像基线重建与业务代码保真设计](tasks/2026-10-11_1520_分层镜像基线重建与业务代码保真设计.md)。在实现并通过专项验证前，保持当前 pinned base，不执行新 base 重建。

需要 PowerShell 7、Git、Node.js/npm、tar 和 OpenSSH 工具；Go 工具链由脚本按 `go.mod` 选择，缺少时从官方源下载并校验 SHA256。服务器需允许 root 的非交互 SSH 密钥登录，且 SSH 主机指纹必须匹配脚本内固定值；脚本不会把密码作为参数传输。
